# Testing strategy
Tests operate on temporary Git repositories, files, SQLite databases and real child processes. Test-only scripted providers exercise deterministic failure and approval paths; no fake provider is shipped in application code. Local HTTP fixtures test the real SSE/embedding adapter without spending provider credits.

The current Phase 2 validation records 132 passing Rust tests and 74 passing frontend tests across nine files. Exact final commands, exit codes, timings and associated logs are indexed by [rust.json](phase2/final/rust.json) and [frontend.json](phase2/final/frontend.json); use those records and their linked test logs if subsequent regressions change the totals. Optional stress and performance tests are separate from the normal passing-test count.

The Rust suite covers capability paths and Windows junctions, UTF-8/binary/size limits, optimistic saves, multi-file stale rejection, rollback and recovery, migrations and DB locks, AST adapters, incremental directory changes, search pagination and malformed regex, graph cycles, Git branches/staging/history, process stdout/stderr/stdin/backpressure/tree termination, command-policy injection, agent approval/cancellation/restart/import and an integrated repository-to-patch-to-test-to-Git workflow. Phase 2 adds malformed and stale protocol envelopes, cancellation during database admission and execution, bounded DNS leases, hostile SSE responses, persistence fault injection, recovery quarantine, worker panic cleanup and a SQL write audit proving cancellation never transiently returns to running.

Property tests cover path normalization, patch apply/revert identity, arbitrary Unicode parsing, policy argument invariants and cosine bounds. The frontend suite covers CAS-save races, stale-save failure, dirty-buffer protection, out-of-order/cancelled searches, explicit command approval, blocked commands, output limits and final-tail draining, selected-patch original hashes, keyboard-binding validation, the desktop-required browser state and command-palette keyboard behavior. Regression coverage also checks graph navigation for references, callers, dependents, affected files and dependencies; disabled unresolved-module navigation; rescan events without concrete paths; edits made during rescan; and the top-100 semantic cap while lexical pagination remains available. Phase 2 checks versioned repository binding, malformed/reordered events, repository-generation races, subscription disposal, coalesced event refreshes and file opens, bounded terminal sessions/chunks, virtualized diff/list scrolling, settings bounds and quoted argument roundtrips. UI/controller tests inject a test-only bridge; they do not establish that a native WebView successfully invokes Rust or loads Monaco workers. Vitest uses at most two workers.

Run the validation commands in README. Run the current performance harness separately with `cargo run -p astraforge-core --release --example phase2_performance -- 1000`; invoke it again with `10000` and `50000` so each scale runs in its own process. It accepts one scale per invocation. The synthetic fixture mixes six languages, malformed sources, Unicode/space paths, ignored and oversized files, watcher bursts and real process output. See the [Phase 2 methodology and results](phase2/performance.md). Timings require hardware/cache/concurrent-load context and do not guarantee performance on a production monorepo. The original `performance` example and [Phase 1 tables](performance.md) remain historical evidence for a different fixture.

The deterministic Rust protocol/stream property suite executes 4,500 generated cases: 1,000 valid UTF-8/SSE streams with two byte-fragmentation strategies each, 500 conflicting duplicate-event IDs, 2,000 bounded arbitrary byte sequences and 1,000 invalid envelopes passed to a real Engine with temporary SQLite. A separate static test checks shared protocol examples. These seeded smoke cases are not coverage-guided fuzzing and are not 4,500 individual test functions.

Four coverage-guided targets under `fuzz/` cover protocol/patch/session deserialization (`protocol`), capability path normalization (`paths`), command classification (`commands`) and incremental SSE decoding (`stream`). With cargo-fuzz and a supported nightly/LLVM environment installed, run `cargo +nightly fuzz run protocol -- -max_total_time=30 -rss_limit_mb=2048 -seed=20260930` from the repository root; substitute each other target name to exercise all four. The [hardening workflow](../.github/workflows/hardening.yml) configures Ubuntu, seeded corpora, two Cargo build jobs, a 30-second budget and 2 GiB RSS limit per target, plus failure-artifact upload. A local Windows GNU libFuzzer build failed in platform-specific C++ code. Linux validation remains pending; the workflow definition and deterministic cases do not establish a successful instrumented run or sustained fuzz campaign.

Native UI end-to-end coverage is distinct from Rust service integration and React component tests. Delivery metadata states separately whether a packaged Windows app was built, launched and exercised. A passing web build does not prove native packaging or live provider compatibility. See the [Phase 2 frontend test log](phase2/final/frontend-tests.txt) for exact counts and the [frontend audit](phase2/frontend-audit.md) for evidence and browser-automation limits.
