# Testing strategy
Tests operate on temporary Git repositories, files, SQLite databases and real child processes. Test-only scripted providers exercise deterministic failure and approval paths; no fake provider is shipped in application code. Local HTTP fixtures test the real SSE/embedding adapter without spending provider credits.

The Rust suite covers capability paths and Windows junctions, UTF-8/binary/size limits, optimistic saves, multi-file stale rejection, rollback and recovery, migrations and DB locks, AST adapters, incremental directory changes, search pagination and malformed regex, graph cycles, Git branches/staging/history, process stdout/stderr/stdin/backpressure/tree termination, command-policy injection, agent approval/cancellation/restart/import and an integrated repository-to-patch-to-test-to-Git workflow.

Property tests cover path normalization, patch apply/revert identity, arbitrary Unicode parsing, policy argument invariants and cosine bounds. The frontend suite has 32 tests across four files, covering CAS-save races, stale-save failure, dirty-buffer protection, out-of-order/cancelled searches, explicit command approval, blocked commands, output limits and final-tail draining, selected-patch original hashes, keyboard-binding validation, the desktop-required browser state and command-palette keyboard behavior. Regression coverage also checks graph navigation for references, callers, dependents, affected files and dependencies; disabled unresolved-module navigation; rescan events without concrete paths; edits made during rescan; and the top-100 semantic cap while lexical pagination remains available. UI/controller tests inject a test-only bridge; they do not establish that a native WebView successfully invokes Rust or loads Monaco workers. Vitest uses at most two workers.

Run the commands in README. Run performance separately with `cargo run -p astraforge-core --release --example performance -- 1000 10000 50000`. Fixtures are synthetic TypeScript repositories, and timings must be interpreted with hardware/cache/concurrent-load information. Do not use synthetic results as a guarantee for a monorepo with large generated files.

Fuzz targets under fuzz/ cover protocol/patch deserialization, path normalization and command classification. Install cargo-fuzz and a supported nightly/LLVM environment, then run `cargo +nightly fuzz run protocol`, `paths`, or `commands` from that directory. Target source is included; sustained fuzzing is not claimed as completed unless a run is recorded in the engineering report.

Native UI end-to-end coverage is distinct from Rust service integration and React component tests. The initial validation report must state separately whether a packaged Windows app was built, launched and exercised. A passing web build does not prove native packaging or live provider compatibility. See the [frontend validation record](validation/frontend-validation.txt) for the exact final frontend counts and the browser-automation limitation.
