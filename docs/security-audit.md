# Security audit

This is an implementation review and regression-test report for the first AstraForge release candidate. It is not a claim of complete penetration testing or operating-system isolation. The review covered Rust agent orchestration, provider transport, repository tools, filesystem boundaries, patch recovery, persistence, watcher integration, and vector freshness. Windows GNU tests were run on the development host; Unix-specific behavior still requires its own CI run.

## Findings addressed during implementation

| Severity | Finding | Change and evidence |
| --- | --- | --- |
| High | A pending `run_test` approval referred to current settings instead of the invocation displayed when approval was requested. Changing test settings could change the approved executable. | `AgentSession.pending_command` now persists the complete `CommandSpec`; `AgentHost.execute_approved` executes that frozen invocation. The regression `approving_a_test_uses_the_frozen_invocation_after_settings_change` passes. See `crates/core/src/agent.rs` and `crates/core/src/service.rs`. |
| High | A concurrent repository switch between checking a session's repository and rebuilding its tool host could attach repository B's tools to repository A's session. | `Engine::resume` captures one `Workspace`, checks the session against its ID, and builds the host from that same captured workspace. See `crates/core/src/service.rs`, `Engine::resume`. |
| High | Agent file reads and searches could send common credential files to the configured provider. An unrestricted agent `git diff` could bypass filtering applied only to the dedicated diff tool. | `service::agent_path_allowed` rejects `.env` variants, common credential dotfiles, private-key and certificate containers, SSH private keys, and `credentials.json`. Agent reads, proposals, history, single-file diffs, search/context entries, and full-diff sections use the guard. Raw agent Git diff output also passes through section filtering. Local editor access remains available. Regression tests exercise the path policy and actual agent tool boundary. |
| Medium | A fifth active agent could be rejected only after a persistent session had already been marked running. A resume could similarly overwrite waiting state before detecting an existing worker. | Capacity and active-worker checks now occur under the transition mutex before persistent state changes. `agent_capacity_rejection_does_not_persist_a_phantom_running_session` passes. |
| Medium | Stop could race a worker's final persistence and allow completed or waiting state to overwrite cancellation. | Stop and worker finalization share the transition mutex; finalization checks the cancellation token, saves cancelled state, and clears pending approvals. The cancellation integration test verifies the provider observes cancellation and persisted state is cancelled. |
| Medium | A provider could declare completion immediately after a patch decision without running verification. | Applied and reverted patch decisions persist `verificationPending`. Completion is refused until a real configured test invocation exits successfully. Failed tests retain the gate; rejecting a patch does not introduce it. The step limit still bounds repeated premature completion attempts. |
| Medium | Finished process output could still have unread chunks after the first poll showing `running=false`. | Agent command collection continues until the finished session also returns an empty chunk batch. Buffer and agent-context truncation are explicitly tracked. See `RepositoryTools::command`. |
| Medium | Overflow rescans and removed directories could leave stale or sensitive embedding rows available to semantic search. | Vector queries now join the current repository/path/content hash in `index_files`; sensitive paths are filtered both before embedding and during search. Prefix invalidation includes directory descendants. See `crates/core/src/vector.rs` and the shared predicate in `crates/core/src/trust.rs`. |
| Medium | Concurrent application instances could write the same database while another instance recovered its patch journal. | `Database` holds an exclusive OS file lock beside the database for its lifetime. A second instance fails with `DB_INSTANCE_LOCKED`; a regression verifies release on close. |

## Enforced boundaries

- Repository files are accessed through a pinned directory capability. Relative-path validation rejects traversal, Git metadata paths, Windows device names, alternate data streams, short-name aliases, and ambiguous trailing characters. Nofollow directory/file opens reject symlinks; Windows reparse points are explicitly rejected. Reads are limited to 2 MiB of UTF-8 text and reject binary data and special filesystem objects.
- File saves use SHA-256 optimistic concurrency checks and same-directory replacement. Patch application records durable before/after snapshots in SQLite before changing files, checks every original hash, verifies results, and rolls back failures. Recovery preserves externally changed files and records `recovery_required` instead of overwriting a conflict.
- AI tools cannot set an approval flag in their protocol. Apply/revert tools produce approval requests; mutation remains an explicit desktop action. Unknown tool fields, including forged approval fields, are rejected. Imported sessions receive new IDs, are marked imported, have pending approvals removed, and cannot be resumed as executable sessions.
- Command execution uses an argument vector and a conservative grammar for automatically permitted Git reads. Other programs require approval. Approved commands remain ordinary user-account processes, with a bounded output buffer and process-tree termination; they are not an OS sandbox. Provider credentials are not inherited by the child environment by default.
- Provider configuration requires HTTPS except for loopback HTTP, rejects URL credentials, and disables redirects. The API credential is read from a named environment variable. Provider frames, generated text, context, embedding dimensions, and embedding batches have limits.
- Prompt context explicitly separates policy, user request, repository data, tool output, and generated content. File reads expose an untrusted-data marker and a heuristic suspicious-instruction marker. These annotations are evidence for the model, not a proof that prompt injection is impossible.

## Remaining limitations and release considerations

| Severity | Limitation | Consequence / next step |
| --- | --- | --- |
| Medium | Provider HTTP transport uses blocking requests and reads with a 60-second request timeout. | Cancellation is checked before requests, between stream frames, and before later agent actions. A blocked socket operation may remain active until it returns or times out. Move transport to an abortable asynchronous request before promising immediate network cancellation. See `provider.rs`, `CompatibleProvider::post` and `stream_chat`. |
| Medium | Sensitive-path filtering is a filename policy, not a content secret scanner. | Secrets can exist in ordinary source files, commit messages, repository memory, or explicitly approved command output. Configuring a remote provider permits transmission of selected context and tool observations. Add content scanning and explicit per-repository disclosure controls for environments requiring stronger protection. |
| Medium | External writers do not participate in the application's mutation lock. | A separate editor or hostile same-user process can race the final hash check and replacement. The journal detects ordinary stale edits and recovery conflicts, but this is not serializable isolation against arbitrary external programs. |
| Medium | Patch snapshots store text and hashes rather than complete filesystem metadata. | Existing-file replacement preserves its permissions, but reverting a deletion recreates the file with normal creation permissions. Original ACLs, extended attributes, and executable-bit restoration for deleted files are not journaled. |
| Medium | The database instance lock is keyed by the database path. | Two deliberately separate application data directories can still target the same repository. Such independent writers are outside the current single-data-directory coordination boundary. |
| Medium | Watcher work uses a bounded queue and can request a full rescan after overflow; a callback already running is not immediately aborted on watcher replacement. | Old work remains repository-ID scoped, but startup/switch, sustained churn, and cancellation during a large rescan need continued stress testing. |
| Low | Agent diff redaction deliberately omits quoted or ambiguous diff headers. | This prevents accidental credential disclosure through uncertain path parsing but can omit legitimate unusual filenames. A complete Git quoted-path decoder is an appropriate follow-up. |
| Low | Durable local records are plaintext SQLite, including approved command output and tool traces. | OS account/file permissions are the protection boundary; database encryption and retention controls are future extensions. No external telemetry is enabled. |

The IPC layer assumes the bundled local renderer is trusted. Repository content must remain escaped text in the UI. The application is not a multi-tenant authorization service; terminal IDs and local diagnostics are application-session resources rather than independent tenant objects.

## Verification

The storage suite covers traversal and reserved paths, binary/encoding/size limits, optimistic conflicts, real create/edit/rename/delete operations, stale multi-file patches, rollback after a later write failure, durable recovery, externally modified recovery conflicts, Windows junction rejection, state persistence, schema-version rejection, and database instance locking. Property tests cover normalized paths and apply/revert identity.

The orchestration integration tests use a real SQLite database and a scripted provider confined to test code. Coverage includes step limits, graph links, trust labels, malformed protocol, forged approvals, command gating and durable tool logs, frozen test invocations, capacity rejection, patch decisions, failed-then-successful verification, rejected patches, provider cancellation, read-only review, failed-tool feedback, restart recovery, and nonexecutable imports. Consult the final validation report for the current executed test count.

The recorded debug-mode patch benchmark used 100 files of 3,600 bytes each: proposal 596 ms, apply 1,066 ms, rollback via revert 796 ms, and SQLite patch-list query 30 ms. These are host observations, not production performance guarantees.
