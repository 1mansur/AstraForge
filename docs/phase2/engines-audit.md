# Phase 2 engine audit
The audit used the Phase 1 production modules and disposable local repositories. The initial regression run reproduced four defects before fixes: unchanged importers retained obsolete dependency targets, a provider response committed after cancellation, automatic Git diff ran a configured clean filter, and automatic Git execution accepted a batch wrapper. The exact initial failures are recorded in [engines-before.log](engines-before.log). The helper fixture writes only a disposable marker and uses a synthetic environment value.
## Changes and evidence
| Finding | Change | Regression evidence |
| --- | --- | --- |
| Dependency targets differed between incremental and clean indexing after target creation/deletion. | Persist raw imports and candidate paths. Re-resolve only affected importers on incremental updates; unchanged full-index sources reconcile their edges. Existing dependency caches migrate from persisted source text. | `dependency_targets_follow_creation_deletion_and_recreation`; `deterministic_mutations_match_a_clean_index` compares six ordered tables after each ten operations in a reproducible 100-operation sequence. |
| Discovery happened before worker serialization, and queued work could not observe cancellation. | Acquire a cancellable index gate before Git enumeration or previous-state reads. Git discovery observes cancellation while waiting for its child. | `cancelled_waiter_leaves_gate_without_acquiring_it`; index cancellation latency in the performance artifact. |
| Watcher and index exclusions differed; replaced watchers could finish obsolete work. | Share exclusion predicate, pass watcher stop token into callbacks, check before delivery, and join workers on shutdown with a self-join guard. Reserved atomic-write temporary files remain excluded. | `watcher_delivers_supported_paths_and_cancels_its_callback` uses real recursive filesystem notifications for virtualenv/cache directories and legitimate AstraForge-like names. |
| Ignored atomic-write traffic saturated the bounded watcher queue, while parent-directory Modify events caused unnecessary subtree scans. | Filter ignored/access events before enqueueing; discard content/metadata modifications to existing directories while retaining topology events and explicit rescan signals. | `ignored_atomic_write_events_do_not_force_full_rescans` and `atomic_file_updates_do_not_rescan_unchanged_parent_directories` both failed before the fix and pass afterward. |
| Each changed path rescanned all repository paths, and candidate lookup preferred a repository-wide covering primary-key scan. | Select exact paths and descendant ranges through the primary key; make the ordinal candidate index cover source as well as repository/path. Migrate old indexes transactionally without rebuilding on every open. | `incremental_file_scopes_do_not_scan_every_repository_row` measures actual SQLite work; directory-range and migration regressions preserve Unicode/adjacent paths and cache contents. |
| Cancellation did not cover queued requests, symbol/filename SQL, or initial SQLite scanning. | Preserve per-request cancellation tokens; use a temporary SQLite progress handler under the database mutex; check cancellation before and after waits and scans. Remove the handler before releasing the connection. | `queued_search_cancellation_applies_to_every_mode`; `external_search_token_remembers_cancellation_before_dispatch`. |
| Symbol offsets counted UTF-8 bytes and text search counted scalar values. | Return UTF-16 columns for the editor. Persist an analysis version so a full index refreshes previous cached AST positions. | `unicode_positions_use_utf16_columns`; `full_index_refreshes_legacy_ast_positions_without_content_changes`. |
| Cancelled or stale embedding responses could commit over fresh state. | Check cancellation after provider return and during the commit transaction. Writes compare the current indexed path/hash, and provider dimensions must agree. | `embedding_cancellation_after_provider_return_does_not_commit`; `stale_embedding_response_cannot_overwrite_a_newer_document`; `inconsistent_embedding_dimensions_roll_back_the_batch`. |
| Automatically allowed Git resolved to a script. | Check the resolved file is a supported native executable before automatic execution; scripts retain the explicit approval boundary. | `safe_git_cannot_resolve_to_batch_script`. |
| Git filters could execute during an automatic diff despite external-diff/textconv flags, and GitService inherited provider environment variables. | Reconstruct the same minimal child environment used by managed commands. Discover configured filter driver names and disable clean/smudge/process execution and required-filter enforcement for built-in invocations. | `git_filters_cannot_run_during_automatic_diff` exercises both GitService and ProcessManager. |
| Blocking stdin could tie up an RPC indefinitely; process completion held the output mutex during SQLite persistence. | Use a four-entry bounded input queue with a dedicated writer. Keep database persistence outside the output lock, terminate the tree at most once, retain/join monitor workers, and reap completed handles. | `process_stdin_backpressure_is_bounded_and_stoppable`; `process_capacity_and_rapid_exits_release_slots`; `simultaneous_stdout_stderr_remain_bounded`; existing real descendant termination and stream tests. |
| Git configuration could redirect later operations after a repository had opened. | Pin built-in and managed Git's effective work tree to the immutable workspace root while preserving the command working directory. Workspace root-marker validation is covered by the storage audit. | `git_worktree_stays_bound_after_configuration_changes`, with a normal subdirectory-relative status assertion; [git-scope-after.log](git-scope-after.log). |
| Windows case-insensitive file creation could miss a case-sensitive candidate lookup, including Cyrillic names. | Register an ordinal Windows path collation, index candidate paths with it, and persist the actual canonical casing of resolved file targets. Unix equality remains unchanged. | `windows_dependency_targets_use_ordinal_case_and_actual_paths`; original failure in [ordinal-before.log](ordinal-before.log). |
| Dense Markdown headings repeatedly scanned source prefixes to calculate lines and lacked the AST-item cap. | Precompute newline positions once, use binary lookup for lines, and reject more than 50,000 extracted items. | `dense_markdown_locations_and_complexity_are_bounded` asserts exact locations and the cap and records timing without a load-sensitive threshold. |
## Method limits
The mutation test is deterministic, with real Git discovery and SQLite transactions; it is not an exhaustive state-space proof. AST references remain syntactic and name based. Dependency candidates do not implement complete TypeScript aliases, Rust macros, Python environment resolution, or language-server type inference. A cancelled index may retain completed batches; it does not publish a completed generation or prune unseen files, and a subsequent full index reconciles the repository.
Regex and literal queries shorter than three characters retain the bounded scan fallback. The SQLite progress callback bounds database work and checks cancellation; the surrounding database remains one serialized connection. Vector search is exact cosine over eligible rows, with a top-100 result cap and per-row cancellation, rather than a production approximate-nearest-neighbor index. The benchmark embedding provider is a deterministic local fixture, so its timing does not predict real provider latency or semantic quality.
Built-in Git operations deliberately bypass configured clean/smudge/process filters, including Git LFS-style transformations. They return raw repository content and do not provide a filter approval flow. The filter inventory and invocation are separate Git processes; a same-user actor concurrently replacing Git configuration is not strongly isolated. Approved commands have normal user-account privileges. The native executable check is not code signing or a general defense against same-user PATH tampering.
The performance harness runs each scale in a separate process and reports the operating-system peak resident set for that benchmark process, including fixture generation. It does not represent the graphical desktop application's peak, GPU allocation, total machine usage, cold-disk performance, or network provider performance. Main database, WAL, and shared-memory sizes are reported separately. All measurements and final check outputs are linked once the runs complete.

## Watcher benchmark investigation
The first mixed 10,000-file benchmark exceeded its existing thirty-second watcher convergence bound; its stderr is preserved in [benchmark-10000-failed.stderr.log](benchmark-10000-failed.stderr.log). An instrumented repeat converged but showed a 14.482-second first callback with only seven reported paths and no full-rescan flag. A focused real-filesystem regression established that one hundred atomic file updates also reported the containing directory, causing a broad subtree reconciliation. A separate blocked-callback regression established that 1,400 excluded temporary-file create/removes could fill the application queue, lose the final real file path, and force a full rescan. The original failed run had no callback trace, so it does not identify which mechanism dominated that particular failure.
The before-fix evidence is in [watcher-parent-before.log](watcher-parent-before.log), [watcher-queue-before.log](watcher-queue-before.log), and [benchmark-10000-diagnostic.stderr.log](benchmark-10000-diagnostic.stderr.log). The final engine suite records twenty-three passing tests and two intentionally ignored subprocess helpers in [engines-after.log](engines-after.log). The final benchmark keeps its thirty-second bound and waits for completed callbacks in addition to persisted file hashes.
The watcher is not lossless. The inspected notify 8.2.0 Windows backend uses a 16 KiB ReadDirectoryChangesW buffer and does not convert a zero-byte completion into an explicit rescan event. Application-queue overflow and rescan flags that are delivered are reconciled, but unreported native-buffer overflow can still require an explicit full index. This dependency limitation is not repaired by filtering the application queue.

## Incremental SQL scaling investigation
The watcher-only fixes passed at one thousand and ten thousand files, but the next fifty-thousand-file run exceeded the same thirty-second bound: a batch of 87 paths took 31.152 seconds and left eleven changes queued. The trace is preserved in [benchmark-50000-failed.stderr.log](benchmark-50000-failed.stderr.log). This trace had no full-rescan flag or directory expansion: it identified true incremental-processing backlog.
Two independent query plans explained work that grew with repository size for every changed path. The previous-path query used OR/substr and only constrained the repository part of its primary key. Candidate lookup selected the covering primary key on repository/source/path, ignoring the non-covering ordinal repository/path index. Exact-plus-binary-range selection and a covering ordinal repository/path/source index remove these repeated scans. The range keeps `directory/` through, but excluding, `directory0`; the empty-root case remains explicit.
The real `IndexService.update` regression seeds fifty thousand persisted paths and candidate rows, changes one hundred real files, and limits work using a SQLite progress handler. Both faulty stages exhausted 5,001,000 VM steps ([scope-work-before.log](scope-work-before.log), [candidate-work-before.log](candidate-work-before.log)); the corrected operation used approximately 757,000 steps, below the unchanged five-million-step budget. This assertion is independent of wall-clock load. The initial dependency-metadata migration check still scans the repository once per update; the fix removes the scan repeated for every changed path.
The independent in-memory query-plan experiment is [index-query-review.json](index-query-review.json). Its timings are microbenchmarks, not the application benchmark, and its collation model is not a measurement of the Windows ordinal callback. Remaining per-file deletes, FTS delete source lookups, and generation/hash lookups use point or indexed prefix selection. Existing-cache migration and repeated reopen are covered by `candidate_covering_index_migrates_without_rebuilding_on_reopen`; the schema version stays unchanged on the second reopen.
