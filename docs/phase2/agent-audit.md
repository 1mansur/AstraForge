# Agent lifecycle and persistence hardening
## Reproduced failures
The initial focused run had five failing tests before production changes. The evidence covers four independent causes plus oversized/identity-invalid persisted data.
| Finding | Reproduction | Impact and correction |
| --- | --- | --- |
| One malformed history row prevents startup | Insert invalid JSON among valid completed and running sessions, then construct `AgentManager` again. | The old all-history decode returned `INVALID_JSON`, preventing application startup. Recovery now reads records individually, isolates invalid rows, preserves raw evidence, and continues with valid sessions. |
| Startup loads every trace at once and trusts embedded identity | Insert a 32 MiB-plus-one-byte row and a structurally valid session whose JSON ID differs from its database row ID. | The old startup collected all JSON strings into one vector and could update a different session ID when recovering. Recovery uses ordered primary-key iteration, checks raw JSON size before decoding, and validates identity, mode, status and graph limits. |
| Failed archive import leaves a session without its archive | A SQLite trigger aborts insertion into `agent_imports` after the session was already saved. | The old method returned an error while leaving an imported session behind. Session and archive insertion now share one transaction; both are absent after failure. |
| Stop rewrites terminal history | Call stop on completed, failed or imported sessions. | The old method changed them to cancelled and erased the summary. These transitions now return `session_state`; already-cancelled sessions are an idempotent no-op. Running, waiting-for-approval and interrupted sessions can be cancelled. |
| A worker panic permanently consumes capacity | Start four real worker threads with a provider that panics. | The old threads exited without removing runtime entries or persisting failure, leaving all four slots occupied and sessions running indefinitely. The worker now catches unwind, writes a structured failure, closes running trace nodes, and removes its runtime entry with cleanup guaranteed on thread-scope exit. |
## Implemented lifecycle changes
Normal execution remains in the existing `AgentManager`, provider and host interfaces. No alternative agent engine or fake runtime provider was added. The adversarial providers and hosts exist only in tests and deliberately panic inside real manager threads; context and tool fixtures read real local files.
Workers are created with fallible `thread::Builder::spawn`. If the operating system rejects thread creation, the inserted runtime entry is removed, the persisted session is marked failed, and a structured `agent_spawn_failed` error is returned. This OS failure branch was code-reviewed; resource exhaustion was not forced on the developer machine.
Cancellation and worker finalization remain serialized by the transition mutex. The runtime map has its own mutex and an independent scope cleanup guard. Caught provider/context/tool panics do not unwind through either manager mutex. The panic payload is not copied into session records; users receive a generic failure plus the public execution trace.
## Startup recovery and quarantine
The new idempotently created `agent_quarantine` table stores original row ID, repository ID, raw data, a reason code and quarantine timestamp. Moving a bad row, removing it from active history and writing its local diagnostic share one SQLite transaction. A failing diagnostic trigger proves that the original row remains available and no partial quarantine is committed; recovery can be retried after the persistence failure is removed.
Startup permits at most 32 MiB of raw JSON per decoded row and at most 1,000 trace nodes / 2,000 edges, with existing imported archives still capped at 8 MiB. It validates that embedded and stored IDs match and rejects unknown modes or states. Previously running sessions become interrupted, and their running trace nodes also become interrupted. Complete, failed, cancelled, imported and waiting sessions retain their state.
Iteration avoids retaining all historical JSON at once. The 32 MiB bound applies to serialized session data, not total working set: parsed strings, structures, serialization and SQLite caches have additional overhead. Quarantined raw data remains in the local database for investigation. It is not silently erased and no new UI to repair quarantined rows is claimed.
## Validation
Seven new adversarial tests pass. The worker-panic regression exercises four concurrent workers at each of three failure points: provider, context collection and tool execution. All twelve sessions become failed, have no remaining running trace nodes, and release capacity; a subsequent healthy task completes after each group.
The focused final test command also runs the existing archive regression and twelve orchestration tests: 20 passing tests in total. New adversarial execution took 1.82 seconds, archive validation 0.80 seconds and orchestration 0.25 seconds in this run, excluding compilation. Actual SQL trigger failures verify archive and quarantine atomicity. Existing tests continue to cover approval binding, read-only review, cancellation, interrupted sessions, bounded steps, malformed/forged actions and required test verification.
## Last cancellation compare-and-set check
A final race test exposed a transient resurrection despite correct eventual cancellation. A real manager worker reads a repository file through a gated test host. The test waits until the host has entered execution, calls `stop`, verifies the persisted cancelled state, and only then installs SQLite `AFTER INSERT` and `AFTER UPDATE` audit triggers and releases the host result. The test waits until the worker drops its host after finalization, then examines every subsequent persisted session status. Before the correction, the recorded sequence was `running`, `cancelled`, `cancelled`; an assertion checking only the eventual state would have missed the failure.
Session persistence now uses one conditional SQLite upsert instead of `INSERT OR REPLACE`. If the existing JSON status is cancelled, the write only succeeds when the incoming status is also cancelled. A rejected write returns the structured `cancelled` error, preventing stale tool, trace, or provider-stream saves from publishing a non-cancelled session. Cancellation finalization can still update cancelled records, and existing resume rules already reject cancelled sessions. The condition is checked by SQLite in the same statement as the write; no separate read/check race is introduced.
The regression fails before this change and passes afterward with every observed status remaining cancelled. Focused agent, orchestration and archive tests pass, as do targeted Clippy with warnings denied and the source-style checker. Evidence is retained in [the failing reproduction](evidence/agent-cancel-before.txt), [the 20-test result](evidence/agent-cancel-after.txt), [Clippy](evidence/agent-cancel-clippy.txt), and [source style](evidence/agent-cancel-style.txt). This protects persisted status; it does not forcibly terminate a host operation that ignores cancellation or roll back an already completed external side effect.
## Remaining limits
- `catch_unwind` handles Rust unwinding panics. Process abort, stack overflow, out-of-memory termination, native crashes and power loss remain restart-recovery scenarios. The default Rust panic hook can still print a panic to local stderr before unwind is caught; its diagnostic is not suppressed by tests.
- A host adapter that never returns and ignores cooperative cancellation can still occupy a worker. The provider transport has separate timeout/cancellation tests in the provider audit.
- If persistent storage itself is unavailable, the worker cannot guarantee writing its final state. Runtime cleanup still runs; a surviving running record becomes interrupted at the next successful startup. Persistence failures remain visible on local stderr.
- This work does not add retention or encryption for valid history, quarantined rows, archives, or traces. Startup time still scales with the number of historical rows, even though it no longer collects all their JSON in memory.
- OS thread-creation failure, transition-mutex poisoning and extreme historical startup memory have not been measured through destructive resource-exhaustion experiments.
