# Storage, filesystem, and patch hardening
## Verified failures and fixes
| Finding | Reproduction and impact | Root cause | Fix and regression |
| --- | --- | --- | --- |
| Unsupported database modified before rejection | Create a SQLite database with `user_version=999` and DELETE journal mode, then call `Database::open`. The old implementation returned `DB_NEWER_SCHEMA` but changed the persistent journal mode to WAL. | Persistent PRAGMAs ran before the compatibility check. | Read and reject unsupported versions before applying persistent settings. The regression now observes unchanged DELETE mode. |
| Legitimate Windows Unicode paths rejected as duplicates | Create distinct NTFS files `K.txt` and `K.txt`, then propose one patch modifying both. The old implementation returned `PATCH_DUPLICATE`. | Unicode lowercase is not Windows filesystem ordinal case comparison. Both strings lowercase to the same key even though native ordinal comparison and this filesystem distinguish them. | Use Windows `CompareStringOrdinal` for the bounded list of at most 100 proposal paths. The regression applies/reverts both files and separately verifies rejection of `K.txt`/`k.txt` aliases. Other platforms retain exact comparison. |
| Local Git configuration redirected workspace capabilities | Configure the selected repository's `core.worktree` to either a sibling directory or an ancestor directory. Both real Git fixtures opened successfully with the wrong root before the fix. | Workspace opening trusted `git rev-parse --show-toplevel` as the filesystem capability boundary. A containment check alone would still permit the ancestor redirect. | Find the nearest actual `.git` directory or regular worktree file above the selected directory and require Git's canonical reported root to equal that marker's ancestor before granting a directory capability or registering the repository. Both redirects now return `PATH_REPOSITORY_REDIRECT`; ordinary repository subdirectories and linked worktree subdirectories remain supported. Bare repositories and discovery without an ancestor `.git` marker are rejected explicitly. |
The first two failures were reproduced before changing production code. The first adversarial run had 8 passing tests, 2 failing tests and one explicitly invoked subprocess helper. After those fixes, all 10 adversarial tests passed in 3.35 seconds; the subprocess helper remains excluded from ordinary direct execution because its purpose is to terminate the child process.
The later workspace-boundary review added four focused tests. The unchanged implementation passed normal/linked worktree and bare-layout checks but failed both redirect regressions. After the boundary fix, all four passed in 0.84 seconds. `workspace-scope-before.txt` and `workspace-scope-after.txt` preserve those separate runs.
Discovery now uses the shared native-executable validation and minimal child environment used by automatic Git commands. Executable lookup excludes the entire verified repository, including when the selected directory is nested. Two isolated subprocess fixtures reproduced an external `git.cmd` wrapper failing to be rejected and a repository-local native executable intercepting nested-directory discovery before the fix; after the fix, the wrapper remains unexecuted and the repository-local executable is skipped. The isolated subprocess changes its own PATH only. The complete final storage suite passed 15 tests in 3.44 seconds, with two child helpers excluded from direct execution; targeted Clippy passed with `-D warnings`.
## Real crash and persistence tests
`crates/core/tests/storage_adversarial.rs` executes the actual patch service and SQLite database. Test-only SQLite functions and triggers provide failure points; application code has no test failpoints or mocked filesystem operations.
A child test executable terminates with exit code 73 without Rust destructor cleanup at six boundaries: before the journal transaction commits, during the final transaction after actual file writes, and immediately after successful completion, for both apply and revert. The parent reopens the database, checks whether the journal should be durable, recovers it, repeats recovery to verify idempotence, checks every file and patch status, and runs SQLite integrity and foreign-key checks. These tests exercise process crashes and SQLite WAL recovery. They do not simulate sudden power loss or failing storage hardware.
SQL `RAISE(ABORT)` triggers separately interrupt journal persistence, final commit, and rollback-state persistence. Final-commit failure restores all touched files. A failed rollback-state commit retains the durable journal, so a later recovery can finish instead of declaring success. Another real callback writes external content at the final-commit boundary; rollback preserves that external content, restores the other file, retains recovery-required state, and succeeds only after manual conflict resolution.
## Abrupt restart during an index transaction
The separately executed `crates/core/tests/index_crash.rs` starts from a completed four-file index, then externally edits, renames, deletes and creates files. A real child opens that database and starts a full index. A test-only temporary SQLite trigger exits the child with code 74 after insertion of a new symbol, following file and FTS writes inside the first batch transaction but before its commit. A flushed marker confirms that exact boundary was reached; normal Rust cleanup does not run.
After reopening, the parent verifies that all seven index tables match the prior completed snapshot, every file retains the completed generation, the interrupted run is recorded, and no run remains running. SQLite integrity, foreign-key checks, FTS external-content integrity and explicit orphan queries pass. Prior text is still searchable and uncommitted new text is absent. A subsequent full index converges to an independently constructed clean index, every persisted hash matches the actual changed files, and old/new full-text queries agree with disk. The focused test passed in 1.56 seconds with its subprocess helper excluded from direct execution; targeted Clippy passed with warnings denied. Raw outputs are [index-crash.txt](evidence/index-crash.txt) and [index-crash-clippy.txt](evidence/index-crash-clippy.txt).
This verifies one real abrupt process-exit boundary in an active first-batch transaction. Larger indexing runs commit batches separately; the test does not claim all-or-nothing rollback across already committed batches, power-loss durability, or exhaustive interruption at every indexing/agent lifecycle boundary. No production injection hooks or index implementation changes were needed.
## Independent incremental-query review
A separate in-memory Python SQLite 3.53.1 probe reproduced two repository-size-dependent query plans using the application's schema, 50,000 paths and 87 changed scopes. This is query-plan evidence with approximate VM instruction counts from a progress callback; its timings are not application wall-clock measurements and do not use the application's bundled SQLite or native Windows collation implementation. The actual Rust VM-budget regression and watcher/index performance runs are reported by the engine audit.
- Previous-path discovery combined equality, an empty-scope branch and `substr` prefix matching inside one OR expression. SQLite used only the repository prefix of the primary-key index: approximately 39,151,300 VM instructions. Separate equality and binary descendant-range branches using `UNION ALL` used both primary-key columns and approximately 2,000 instructions for the same 87 results.
- Affected-importer lookup selected `source` while matching candidate `path` with the custom collation. Without planner statistics, SQLite preferred the covering primary key restricted only by repository over the non-covering `(repository_id,path COLLATE astra_path)` index: approximately 17,400,900 instructions. Including `source` in that ordinal index made it covering for the equality lookup and reduced the count to approximately 1,300 instructions. Merely editing an existing `CREATE INDEX IF NOT EXISTS` definition would not migrate the old index.
Every inspected changed-file cleanup DELETE and the FTS delete-source lookup used its path/source primary key or dedicated index. The dependency migration anti-join still inspects repository rows once per update, but its correlated inner lookup uses `(repository_id,path)` and is not repeated for each changed file. [The query-plan artifact](evidence/index-query-review.json) contains the exact SQL, plans and measured counts for both 10,000- and 50,000-row fixtures. The probe script remains in the working evidence directory; production changes and correctness tests belong to the engine work.
## Shared-state and concurrency review
| Resource | Owner and synchronization | Cancellation, failure, cleanup |
| --- | --- | --- |
| SQLite connection | `Database`, one connection protected by a mutex; WAL, FULL synchronization, five-second busy timeout | Rust transactions roll back when an operation returns an error. Mutex poisoning returns a structured error. The adjacent exclusive lock is held for the database lifetime. |
| Repository capability | Cloneable `Workspace` with an `Arc` directory capability | Reads validate path components and bound regular UTF-8 files. Application mutations use the global mutation mutex. Handles release when the last workspace clone drops. |
| Patch mutation and recovery | `PatchService` plus the same global mutation mutex | No mid-operation cancellation is exposed. A proposal or operation either returns a terminal result or retains its durable journal. Divergent external content is preserved. |
The reviewed call sites acquire the mutation mutex before database access; no opposite acquisition order was found. The global mutex also serializes unrelated repositories, so it can cause contention. It does not synchronize external editors, separately configured application instances, or arbitrary same-user software.
Eight concurrent applications of the same patch produce exactly one success and seven `PATCH_STATE` errors. Eight compare-and-swap saves produce exactly one success and seven stale-file errors; the successful result matches the final disk content. Six database workers execute 240 transaction attempts, deliberately aborting every seventh operation; the final row count equals committed transactions, failed transactions leave no rows, and patch foreign keys reject an orphan repository reference.
## File bounds and property coverage
The harness tests files with logical sizes of 1, 10, 50, 100 and 500 MiB using `set_len`, without constructing corresponding in-memory buffers. The 1 MiB zero-filled file is rejected as binary; larger files are rejected from metadata as too large. A valid UTF-8 file exactly at the 2 MiB limit still loads. These tests verify safe rejection and code-path bounds, not native Monaco performance or peak resident-memory measurements.
A 256-case property test generates arbitrary Unicode paths and checks that every accepted normalized path remains relative, has only ordinary components, respects the byte limit, and is idempotently normalized. Existing tests separately cover traversal, Windows device/alias names, junctions, binary/encoding rejection, stale multi-file patches and apply/revert identity.
## Residual limits
- The final content check and replacement cannot form one transaction with unrelated filesystem writers. External processes can race after a check; rename and deletion have comparable OS-level limitations.
- Windows comparison follows the existing case-insensitive policy. Case-sensitive Windows directories remain a layout limitation; this change does not claim support for distinct ASCII case variants within them.
- The Windows implementation does not explicitly flush directory metadata. Process-crash success does not prove power-loss durability.
- A hard crash between temporary-file creation and replacement can leave an unreferenced temporary file. Recovery does not delete files merely because their names resemble internal temporary names, since that could remove unrelated user data. Persisting temporary-file ownership would be a further change.
- Patch snapshots preserve text. Deletion/recreation does not restore every platform ACL or executable metadata field.
- Many non-patch domain tables still lack foreign keys. Their consistency depends on service transactions and cleanup; patch foreign-key tests do not establish all-domain referential integrity.
- No kernel fault injection, disk-full filesystem, network-mounted filesystem, or hardware failure campaign was run for this storage slice.
